# HTTP协议的局限性

AJAX 和 Comet 都使用 HTTP 作为底层传输协议。**HTTP 最初的设计目的是为了以请求-响应的方式提供超媒体资源。** HTTP协议并没有针对**实时应用**进行优化，而实时应用通常涉及高频或持续的客户端-服务器通信，以及对变化做出即时响应的能力。

## 可扩展性有限

- HTTP轮询是指以固定的时间间隔向服务器发送请求，以查看是否有新的更新需要获取。高轮询频率会导致网络流量和服务器负载增加；这种方式扩展性较差，尤其是在并发用户数量增加时。
- 低轮询频率对服务器的负担较小，但可能会导致提供过时的信息，这些信息可能已经失去了部分价值。

总结为：长轮询增加网络流量和服务器负载。短轮询负担低，但会获取过时数据。

## 不可靠的数据订阅和数据送达的保证

可靠的消息顺序可能是一个问题，因为同一客户端可能同时发出多个 HTTP 请求。由于网络状况不稳定等各种因素的影响，无法保证客户端发出的请求和服务器返回的响应能够按正确的顺序到达目的地。还有就是服务器可能发送了响应，但网络或浏览器问题可能导致消息无法成功接收。为此需要添加一种消息接受确认机制。

## 延迟

首先建立HTTP连接需要很长时间,建立客户端和服务器端连接的过程涉及大量的来回握手和通信。

HTTP的请求发送是按照顺序发送的。只有在收到当前请求的响应后，才会发送下一个请求。根据网络状况，**客户端收到响应**和**服务器收到下一个请求**之间可能会存在延迟。

所以建立连接存在延迟，按照固定顺序发送请求，接收响应的过程也存在延迟，这些延迟就会导致用户的体验非常糟糕。

tips: SSE流式传输技术更能降低延迟，但自身收到请求头部信息限制，头部信息同样会增加消息大小并导致不必要的延迟。通常,响应中的**HTTP头部信息**比实际传输的**核心数据**更大。

## 不支持双向流媒体(与WebSocket协议的最大区别)

HTTP 协议本质上是一种请求/响应协议，它不支持客户端和服务器在同一连接上进行双向、始终在线的**实时通信**。

通过建立并使用两个HTTP连接可以来模拟双向实时通信，但同时维护两个连接会给服务器带来非常大的开销，因为服务单个客户端意味着要消耗双倍的资源。
